Product Documentation · Verilume

Copywriting

The AI copywriting engine behind every generated word in the portal: Brand Voice, Creative Job, Campaign Copy, and PR & Corporate Copy. Two mechanisms share the same generation surface — a blind multi-vendor panel ("interview" a contest of AI candidates, pick a winner) and single-draft generation for everyday requests. This document is the current-state reference for that Product — what's actually built and running today, verified against the live codebase, written to be absorbable by engineering leadership without prior context.

Owner Todd Brown System verilume.ai — backend/server.js Verified against production code, 2026-09-12 Status Live in production

The four contest surfaces§ 01

Every AI copy surface in the portal that runs a multi-vendor blind panel ("interview" candidates, review, select a winner) uses the same underlying mechanism. This is the literal product surface a client or team member interacts with.

Voice Contest is the flagship and the one that established the pattern: its winning Vision Statement and Longform Example become accounts.visionStatement / accounts.longformVoiceExample, which every other generation prompt in the file already reads as brand context — see § The content loop.

Vendor dispatch & the AI panel§ 02

Anthropic (Claude) is the default vendor for every surface. Contest panels additionally dispatch to whichever of four other LLM vendors have API keys configured, run in parallel, and returned as blind candidates. Full vendor list, env vars, and licensing status now live in one place — see Licensed Integrations — rather than duplicated here where it can drift out of sync.

Design policy — never reveal the winning model to the client

Candidates are shown blind (labeled generically, not by vendor/model) in every client-facing contest panel. This policy is also enforced in the fallback path: when a stored vendor preference references a vendor whose key has since been removed from the deployment, the dispatcher falls back to Anthropic/template silently rather than surfacing which vendor was lost.

Registry & single entry point§ 03

Todd: "all contests whether is exists today or not needs to have the same structure when recording results or we can't scale the data." A new contest feature registers one entry — that's the whole integration point.

01

A contest's /select endpoint fires

A team member picks a winner from the blind candidate panel, on any of the four surfaces.

02

One call: recordContestResult()

Resolves the contest's CONTEST_TYPE_REGISTRY entry (its taskType and known subtypes), then does both things a contest result needs, together, so they can never drift apart.

03

Writes the ranking ledger

Full rank order, every candidate, this run — see § Ranking ledger.

04

Upserts the priority-model cache

Current winning vendor for this account/taskType — see § Priority-model cache.

Creative Jobcreative_jobCopywriting
Campaignmarketing_copyOffer, Brand Campaign, Launch, General

function recordContestResult(accountId, contestType, contestSubtype, chosen, allCandidates, sourceTable, sourceInterviewId, setBy){
  const reg = CONTEST_TYPE_REGISTRY[contestType];
  if (!reg){
    console.error(`recordContestResult: unregistered contestType "${contestType}" — add it to CONTEST_TYPE_REGISTRY so future contests stay on the same structure.`);
  }
  logContestRanking(accountId, contestType, contestSubtype, sourceTable, sourceInterviewId, allCandidates, chosen.key);
  try {
    upsertPriorityModelFromCandidate(accountId, (reg && reg.taskType) || contestType, chosen, sourceTable, sourceInterviewId, setBy);
  } catch (e){ /* priority-model bookkeeping should never break the select response */ }
}

Ranking ledger§ 04

Todd's correction after a first draft tracked only the winner: "I thought the purpose of ranking was to support more advanced modeling in the future. Why would rank 1-5 if we didn't build anything to support it?" Full rank order is now captured for every run.

Ranking basis, chosen automatically per contest

Rating (Voice Contest) > combined score (Creative Job / Campaign Copy) > compliance score alone (PR Copy, where nothing stronger exists yet). Ties share a rank number. Unconfigured or errored candidates are excluded from ranking.

idTEXT (PK)Row identifier

contestTypeTEXTRegistry key
contestSubtypeTEXTe.g. Offer, Press Release, Copywriting
sourceTable / sourceInterviewIdTEXTWhich contest run produced this row
candidateKey / vendor / modelTEXTWhich AI candidate this row scores
rankINTEGERFull rank order (1 = best) — ties share a rank
isWinnerINTEGER1 for the selected candidate, else 0
rankBasisTEXTrating / combined_score / compliance_score
createdAtTEXTTimestamp of the /select action

Indexed on (accountId, contestType, contestSubtype). Append-only — one row per candidate per contest run, never overwritten.

Priority-model cache§ 05

Gap closed this cycle

account_priority_models is the "current winning vendor per taskType" cache — one row per account/taskType, upserted every time a contest is decided. Before this round, only 2 of 4 contest types ever wrote to it.

Has a real dispatch consumer today

generateMessagingCopyViaAI() (Campaign Copy single-draft) and draftPrCorpCommCopyViaAI() (PR/Corporate single-draft) both call getDispatchablePriorityModel() and route to the account's winning vendor when one is on file and still configured — falling straight through to Anthropic on any dispatch failure or stale reference.

Recorded, no dispatch consumer yet

Creative Job copy is only ever produced via its own contest panel; Voice Contest is a one-time-per-account comparison, not a per-request draft. Their vendor preference is still recorded for consistency and future reporting — same "capture ahead of the consumer" posture as the ranking ledger itself.

The content loop§ 07 — already live, clarified not new

Working as designed

Separate from vendor/model preference: the actual winning content from Voice Contest already feeds every other generation prompt as brand context.

Confirmed present via direct code search

account.visionStatement and account.longformVoiceExample (saved to the account on Voice Contest's /select) appear as "BRAND VISION STATEMENT" / "REFERENCE LONGFORM EXAMPLE" blocks inside buildInterviewPrompt() (Creative Job / Campaign Copy contest generation), generateMessagingCopyViaAI() (Campaign Copy single-draft), draftPrCorpCommCopyViaAI() (PR/Corporate single-draft), and the Draft Scoring prompt.

This is the primary way "the ideal voice influences all copy" already works today — the vendor-preference loop is a second, separate lever on top of it (which model does the writing), not the only mechanism.

Weekly usage cap§ 08

A single, shared safety cap on AI panel usage — not a quality limit — sits in front of all four contest surfaces.

INTERVIEW_WEEKLY_CAP (default 20/week/account)
checkInterviewWeeklyCap(accountId)

Rolling 7-day window, counted across Creative Job, Campaign Copy, PR Copy, and Voice Contest together — running one panel on any surface counts against the same shared total. Called at the top of all four contest-run endpoints; when the cap is hit, the request is rejected with a message naming the current usage and reset window rather than a bare error.

Known gaps & open items§ 11 — for product awareness

None of these have been fixed yet — listed here so the product team can prioritize, not because a fix has already shipped.

⚑ No UI for the ops reader

GET /api/ops/contest-rankings is an API response today, not a dashboard. Building a simple win-rate view on top of it is the natural next step.

⚠ No automated action on win-rate data

No auto-promotion of a consistently-winning vendor across accounts — current state is visibility and consistent capture, not an automated policy.

⚠ Creative Job still has no per-request dispatch consumer

Creative Job's recorded vendor preference has no equivalent single-draft generation path to check it yet — recorded for consistency and future reporting, same posture as the ranking data itself. Voice Contest closed this same gap 2026-09-12 (generateVoiceGuideDraftViaAI() now checks getDispatchablePriorityModel(accountId, 'brand_voice') — see §12), leaving Creative Job as the only remaining contest type without a consumer.

⚠ No automated alerting on vendor-model deprecation

The Gemini model retirement this cycle (§02) was caught by reading a live 404 response body, not by any monitoring. A vendor deprecating a model silently degrades that panel candidate until someone notices.

⚠ Corporate Comms' audience field is still free text

Press Releases now have a controlled audience taxonomy (Consumer / Business & Trade Network). Corporate Comms kept its original free-text audience field, unchanged — worth unifying if Corporate Comms is ever audited the same way.
