Company Profile & Team

This Product group covers company and team assessments, business-profile workstreams, channel-level assessments, and reputation/PR. This first edition documents only the one sub-area that reached a real, verified, shipped state this cycle — the Verilume Wealth Index on Company Overview — and says so plainly rather than padding out sections for the other three, which remain genuinely not yet built or not yet documented. See § Not yet documented.

Owner Todd Brown System verilume.ai — frontend/assessment.html, frontend/portal.html, backend/server.js Verified against working tree, 2026-09-12 Status Wealth Index section: built; not yet deployed (see the home page)

Headline findingsthis cycle

Prompted directly: "I don't see the Verilume Wealth Index. The portal page that is supposed to contain the information is above" (two Company Overview screenshots). Checked against the real assessment/portal/backend code, not against what was planned.

Root cause found

The number was never sent to the backend

assessment.html computed a real Verilume Wealth Index client-side during the Free Assessment, but buildScorecardPayload() only ever sent the derived audience/wealth tri-select — never the raw target-income slider value the index is computed from. The number could never be reconstructed or shown anywhere after account creation.

Fixed this cycle

Raw income now travels and persists

New accounts.wealthIndexTargetIncome column, sent from the assessment, editable on Company Overview, and rendered with the same formula the assessment itself uses — see § The Verilume Wealth Index formula.

Working as designed

Honest empty state, non-forcing suggestion

An account with no income on file shows a plain "not set yet" note, never a fabricated number; a Luxury/Mass-Market suggestion nudges the slider without silently overwriting a value the client already chose.

Not covered here

Three sub-areas remain undocumented

Assessment & Scoring Engine, Reputation & PR Monitoring, and Team Roster & Org Profile are real gaps in documentation, not confirmed-absent features — see § Not yet documented.

The Verilume Wealth Index formula§ 01

One formula, implemented twice — once in assessment.html (built earlier, documented in cxmedia-assessment-step2-step5-rebuild-2026-08-31.md in the Claude project) and ported byte-identical into portal.html this cycle so Company Overview shows the exact same number the Free Assessment did, not an approximation.

StepWhat it doesNotes
nationalAverageIncome()Weighted-mean U.S. household income off 16 Census income brackets (INCOME_BRACKET_BOUNDS/INCOME_BRACKETS_FALLBACK_SHARES) — ≈$97,900 off the fallback sharesportal.html's port is fallback-only (no live Census call); assessment.html can also use live data
generationWealthMultiplier()Average of GENERATION_WEALTH_INDEX (Fed SCF-sourced) across the account's selected generation(s), or 1.0 for "general"Gen Z 0.20, Millennial 0.47, Gen X 1.32, Boomer 1.82, Silent 1.74 — Gen Alpha/Beta/Greatest are estimate/placeholder values, flagged as such in the source
verilumeWealthIndex(targetIncome)round((targetIncome / nationalAverageIncome()) × generationWealthMultiplier() × 100)100 = the average U.S. household; deliberately uncapped, not clamped to a tier's midpoint
wealthIndexLabel(index)≥200 High Net-Worth/Luxury; ≥130 Wealthy; ≥70 Mainstream Affluent; else Value-ConsciousDisplay label only
deriveWealthTiersFromIndex(index)Maps the 4-band index back to the 3-key hnw/wealthy/middle shape every existing downstream consumer expectsThe bridge between the new numeric index and the pre-existing tri-select — see § Who reads it downstream
⚠ Two independent implementations, kept in sync by discipline, not by code sharing

assessment.html and portal.html are two separate, unbundled front-end files with no shared module system — the formula was ported by hand and confirmed byte-identical at build time, but nothing prevents the two copies from drifting apart on a future edit to one file only. See § Known gaps.

How a client sets it§ 02

01

Free Assessment — household income slider

A visitor sets a target household income (state.targetIncome); the assessment computes and shows the index live during the flow.

02

Sent and persisted at account creation

buildScorecardPayload() now includes wealthIndexTargetIncome: state.targetIncome alongside the existing audience/wealth fields; the backend stores it on the new accounts.wealthIndexTargetIncome column (REAL, nullable — no value means "not set," never a fabricated 0).

POST /api/accounts
03

Shown and editable on Company Overview

A "Verilume Wealth Index" block ($15,000–$250,000 slider, live-recomputed number, band label, and a non-forcing Luxury/Mass-Market suggestion) renders inside the existing Company Overview card. An account with no value on file shows an explicit empty-state note instead of a guessed number.

renderCpWealthIndex() / cpUpdateWealthIndexSlider() / cpApplyWealthIndexSuggestion()
04

Saved back on profile update

saveCompanyProfile() sends wealthIndexTargetIncome in the same PATCH as the rest of Company Overview; the backend's merge-update convention keeps the existing value when the field isn't present in a given request.

POST /api/accounts/:id/profile

Known gaps & open items§ 06 — for product awareness

⚠ Formula exists in two unbundled files

assessment.html and portal.html each carry their own copy of the Wealth Index formula. A future change to one (a new income bracket, a revised generation multiplier) must be manually mirrored to the other or the two surfaces will quietly disagree.

⚠ No backfill for pre-existing accounts

Any account whose assessment ran before this cycle has no wealthIndexTargetIncome on file and shows the honest empty state everywhere that reads it (Company Overview, Store Trade Area Qualified) until someone sets it manually on Company Overview. No bulk backfill tool exists.

Suggested next steps§ 08

  1. Research and document Assessment & Scoring Engine, Reputation & PR Monitoring, and Team Roster & Org Profile as their own sections or their own docs — the largest open item in this Product group.
  2. Consider a shared formula module (or at minimum a single source-of-truth comment block referenced by both files) so the Wealth Index formula can't silently drift between assessment.html and portal.html.
  3. Decide whether a backfill pass is worth building for pre-existing accounts with no household income on file, or whether the honest-empty-state posture is the permanent answer.
