Registration & Account Management

The subsystem that gets a client from "never heard of Verilume" to a logged-in, correctly-isolated account: signup, identity verification, login, step-up MFA, password recovery, session lifecycle, and the Twilio and HubSpot integrations that ride alongside it. This document is the current-state reference for that Product — what's actually built and running today, verified against the live codebase rather than against what was planned.

Working as designed

Signup verification gate

Account creation hard-requires a consumed, matching Twilio/email verification code — one verified code produces exactly one account.

Signup & identity verification§ 01

Account creation is gated end-to-end by a verification code — a new account cannot be created without first proving control of the phone number or email on the registration.

01

Registrant submits signup details

Business info + a contact method (phone preferred, email fallback) is collected client-side.

02

Verification code sent

Server sends a one-time code via Twilio Verify (SMS) when configured, or falls back to an on-screen "interim" code when Twilio isn't configured for the environment.

POST /api/auth/verify-signup-code
03

Code checked, verification row consumed

On a correct code, the server marks verified=1 on that verification row and returns a verificationId the client must carry into registration.

04

Account creation, hard-gated

Registration is rejected unless it carries a verificationId whose row is verified=1 and consumedAt IS NULL, and whose verified target (phone/email) matches the registration. The row is then marked consumed — enforcing "one verified code → exactly one account," with no replay.

POST /api/auth/register-admin
05

Lead synced to HubSpot

Registration also feeds the HubSpot sync (see § HubSpot) — non-blocking, doesn't fail the signup if HubSpot is down.

Login & step-up MFA§ 02

Password + device trust decide whether a login completes immediately or requires a second factor. This is real and currently wired — not a placeholder.

01

Credentials submitted

Email/password checked against the account.

POST /api/auth/login-user
02

Trusted-device check

Server checks for a valid trusted_devices token for this browser/device (30-day lifetime, independent of session lifetime). Valid trust → session issued immediately, no MFA prompt.

03

No trusted device → MFA required

Server sends a code (SMS if a phone is on file, otherwise email) and responds with { mfaRequired: true, verificationId } — no session is issued at this point.

04

Code verified → session created

Only this call actually creates the session and (optionally) marks the device trusted for future logins.

POST /api/auth/verify-login-code
⚠ Recovery dead-end

A team member with no phone number on file and no access to the account email has no path through step-up MFA today. Flagged in § Known gaps.

Sessions & logout§ 04

Session mechanics

sessions table: token (PK), accountId, memberId (nullable — null for the account admin), createdAt, expiresAt. 7-day lifetime, minted by createSession(). authenticate(req) reads Authorization: Bearer <token>, looks the row up, and lazily expires stale rows on read.

Client-side pointers

Per-account bearer token is stored under verilume_session_<accountId> in localStorage. A separate key, verilume_active_account, is the sitewide "who's currently logged in" pointer — found to be set inconsistently (forgot-password.html's persistSessionFor() never sets it), which is the likely root cause of the "logged in as the wrong account" symptom reported and fixed earlier this cycle.

Twilio — SMS & Verify§ 05

Used exclusively for one-time verification codes (signup and login MFA) — not for general notifications.

Configuration

All three of the following must be set for Twilio to be considered configured (TWILIO_CONFIGURED). If any is missing, the platform falls back to an "interim" on-screen code instead of sending SMS.

TWILIO_ACCOUNT_SID TWILIO_AUTH_TOKEN TWILIO_VERIFY_SERVICE_SID

Functions

FunctionRole
sendVerificationCode()Starts a Twilio Verify check for a phone number
checkVerificationCode()Confirms the code the user submitted against Twilio
⚠ Interim fallback exposes the raw code

When Twilio isn't configured, the "interim" fallback code is hashed at rest, but the raw code is returned directly in the live JSON API response body so the frontend can display it on-screen. Acceptable for a demo/interim environment; worth a second look before this fallback is ever reachable in a fully-configured production account.

Production status

Twilio credentials are present in the Vercel production environment (confirmed via the Aug 21 environment-variables screenshot), but as of this writing the integration has not been exercised end-to-end with real credentials in production — flagged as a follow-up in § Known gaps.

HubSpot — CRM sync§ 06

Server-side-only sync of leads/accounts into HubSpot contacts — the browser never talks to HubSpot directly.

HUBSPOT_ACCESS_TOKEN HUBSPOT_SEND_CUSTOM_PROPERTIES

What triggers a sync

  • POST /api/leads — new lead capture
  • POST /api/leads/enhance — enriched lead data

Both call syncLeadToHubspot() synchronously inline in the request, which posts to a single HubSpot endpoint:

POST https://api.hubapi.com/crm/v3/objects/contacts/batch/upsert
Failure behavior

HubSpot sync never blocks or fails the user-facing flow — if the HubSpot call errors, the lead/registration still succeeds. There is currently no retry logic, so a HubSpot outage silently drops that sync rather than queuing it for later.

Multi-tenant data isolation§ 07 — validated

Confirmed solid

Requested validation: "how we protect client data from mixing with other clients." Checked directly against the code, not against documentation of intent.

Enforcement mechanism

A single function, requireAccount(req, res, accountId) (server.js, line 4351), is the consistently-applied server-side gate. It is called 113 times across the codebase. Every account-scoped, data-touching route either checks the URL-supplied accountId directly against the caller's session, or — for child resources like creative_jobs, team_members, and invoices — first resolves the resource's true owning accountId from the database, and only then checks it. A client can never supply an accountId and have it trusted at face value.

Two legitimate exceptions

RouteWhy it's global by design
/api/market-population-master*Shared reference/master data, not client-owned
POST /api/leadsPublic lead-capture endpoint, pre-account by definition
Enforcement layer

Isolation is 100% application-layer — there is no Postgres Row-Level Security (RLS) underneath it. This matches what was already documented as current-state (vs. planned) in the master technical architecture doc. It's a real and working control today, but it means every new account-scoped route must remember to call requireAccount() — there's no database-level backstop if one is missed.

Data retention & purge on contract end§ 08 — validated

Not implemented

Requested validation: "permanent vs. passive purge processes when contracts expire." This is the most important finding in this document — the capability does not exist in the running system today, despite being planned and discussed.

⚑ Nothing found in code

A direct search of backend/server.js and frontend/ops-console.html turned up none of the following:

  • Soft-delete or hard-delete on any account-level record
  • An account-level status field (Active / Suspended / Terminated)
  • A contract/subscription end-date field (e.g. accountEndDate)
  • An "export all client data" endpoint
  • Any retention-window or scheduled cleanup job (cron or otherwise)

What exists instead

ops-console.html displays an ACCOUNTS object with account status shown in the UI — but it's a hardcoded mock, explicitly commented in the source as illustrative, and is not wired to any backend endpoint. Changing a status there today would change nothing about the underlying account or its data.

What was planned but not built

Account lifecycle controls (status transitions, admin-level lifecycle actions) were scoped and documented on 2026-08-18, but implementation has not shipped. This gap should be treated as a real product requirement, not an oversight — until it's built, there is no technical mechanism to purge or export a client's data when a contract ends; any such action today would be entirely manual (direct database intervention).

Known gaps & open items§ 10 — for product awareness

Surfaced by this cycle's research. None of these have been fixed yet — they're listed here so the product team can prioritize, not because a fix has already shipped.

✓ Fixed 2026-08-22 — privilege escalation via isAdmin

Originally flagged here (2026-08-21 draft) as a live account-takeover path: requireAccount() confirmed a caller belonged to the account but never checked isAdmin, so any logged-in team member could self-promote, demote the real admin, reissue the admin's login credentials, or invite a new admin. Closed the next day with a new requireAdminMember(req, res, accountId) (server.js) — re-authenticates the caller, and for a real memberId session re-reads team_members.isAdmin from the database on every call (never trusted from the session token, so a revoked admin flag takes effect immediately); a legacy account-level login with no memberId is treated as root-equivalent, same as requireAccount() already did. Verified gating each of the four actions this cycle: PATCH /api/team/:id requires it only when isAdmin is actually changing (so a non-admin can still edit their own name/email/level); DELETE /api/team/:id; POST /api/team/:id/reissue-credentials; and POST /api/accounts/:id/team when the invite itself requests isAdmin:1. This document sat drafted-but-undeployed for three weeks (see meta above) — a reminder to redeploy a doc promptly, since a stale flagged vulnerability read as still-open is its own kind of misinformation.

⚠ No rate limit on password-reset requests

POST /api/auth/request-password-reset can be called without limit, opening it to enumeration/abuse.

⚠ MFA recovery dead-end

A team member with no phone on file and no access to the account's email has no documented recovery path through step-up MFA.

⚠ Twilio credentials unverified in production

Env vars are present in Vercel, but the integration hasn't been exercised end-to-end with real credentials in production yet.

select-tier.html exists but isn't linked from anywhere on the live site. A previously-noted pasted Twilio Auth Token needs rotation confirmation. Suggested next steps§ 12

  1. Build the account lifecycle/retention layer — status field, contract-end date, and an explicit purge-or-export action, wired to a real backend (not the current mock). This is the direct answer to "how do we handle data when contracts expire," and today the honest answer is "manually." Still open as of 2026-09-12 — the highest-priority remaining item in this document (the isAdmin gap that used to lead this list was closed 2026-08-22; see Known gaps).
  2. Add rate limiting to request-password-reset.
  3. Exercise Twilio end-to-end in production with real credentials before relying on it for a live client.
  4. Decide on an MFA recovery path for team members without a phone on file.
