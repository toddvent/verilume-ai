How the database is organised

One shared Postgres database (Supabase) holds every client. Nearly every client table carries an accountId, and the server routes that read client data check that the signed-in session belongs to that account (requireAccount) or that the caller is Verilume staff. A full route audit was done in November 2026. There is no separate database per client. SQLite is used only for local testing; production runs on Postgres. Some columns are stored in lowercase by Postgres, so the server reads them through a helper (aliasVal); that is why you will see both accountId and accountid in the lists.

New tables are created by the server on start-up. A table can be added by shipping a new release; nothing is changed by hand in the database.

How it is protected

  • Row-level security is on for every table. No policies are defined, so the public database keys can read nothing. Only the server's own database role gets in. New tables are switched on at creation and a sweep re-checks every 10 minutes, turning it on for any table that slipped through.
  • Passwords and access codes are never stored. Only a salted scrypt hash and the salt are kept (passwordHash, passwordSalt, accessCodeHash, accessCodeSalt). The same applies to emailed and texted sign-in codes (codeHash, codeSalt).
  • Access is logged. Data access is recorded in account_data_access_log and Verilume team actions in platform_access_log.
  • Money-related changes are append-only. financial_audit_log has no edit or delete route.
  • Upload scan results are recorded on uploaded_files (personal-data findings, virus scan status and provider). An upload with no working scan (no ClamAV, no Cloudmersive key) is rejected, unless a dev-only bypass flag is set, so confirm a scanner is configured in production or uploads will fail.

Retention

Only some data is removed automatically. Everything else stays until a client account is deleted by an Owner or IT user. A written Data Retention and Deletion Policy (v1.0, 2026-10-09) is in the Library. It does not mention the 180-day purge of upload archives, and says automated purging is still planned, so the two should be reconciled.

Known gaps

  • Some tables carry the same column twice under different capitalisation in the live database (for example campaigns has both roleStyle and rolestyle). This is harmless but untidy; a clean-up migration is not scheduled.
  • Retention policy exists but does not match the code (the 180-day upload-archive purge is not in it); most tables are kept until account deletion.
  • Uploaded files and logos are stored inside the database as text (dataUrl, datab64); large clients will need object storage.
  • Row-level security has no policies by design. If the app ever queries from a browser with a public key, policies must be written first.
  • The "sensitive columns" list comes from column names. A column holding personal data under an unexpected name would be missed.
