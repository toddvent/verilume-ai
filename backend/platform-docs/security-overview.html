What we can tell a client today

  • Each client's data is kept in separate account records, and the server checks the signed-in session on every request for that account. Verified
  • Passwords, access codes and sign-in codes are stored only as salted hashes, never in readable form. Verified
  • Sign-in uses a second step: a 6-digit code sent by email, or by text where the person has turned that on. A device can be remembered for 30 days. Verified
  • Repeated wrong passwords pause sign-in (10 attempts for one name or 40 from one network in 15 minutes). Verified
  • Every database table has row-level security on, so the database's public keys can read nothing. 198 of 198 tables, checked live. Verified
  • The client portal and the team console are served only after sign-in, marked so each load can be traced to a person, and logged. Verified
  • Connections to the service use HTTPS; the server sends a strict-transport header. Verified
Do not say yet: SOC 2 certified or in audit, penetration tested, single sign-on, that data is encrypted with client-held keys, anything about the scanner vendor beyond what the Vendor policy lists (Cloudmersive has no attestation recorded), or that vendors do not retain or train on client content (vendor terms have not been recorded here). Terms of Service and Privacy Policy are still placeholders awaiting legal review.

Keeping clients apart

  • 160 of 198 tables carry an account id; the rest are shared reference data, Verilume-team tables or logs. See Database architecture.
  • Client routes call requireAccount, which rejects any session whose account does not match the request. Verified
  • A November 2026 route audit (releases r67 to r91) closed routes that had been open to anyone and gated the portal and consoles behind sign-in. Verified (see the IP protection log in the 2026-11-17 readout note)
  • Row-level security is on for every table with no policies, and a sweep re-checks every 10 minutes. Verified
  • There is an emergency switch (ACCESS_ENFORCEMENT=off) that turns off the per-person data-access rules. It is for outages only and should stay unset.

Logging and audit

  • platform_access_log: who on the Verilume team did what in which client account, with IP.
  • account_data_access_log: reads of client data records with the actor and record count.
  • financial_audit_log: spend approvals and money-related changes; append-only, no edit or delete route.
  • portal_serves: every load of the portal or consoles with the person, IP, browser and a per-load watermark.
  • legal_acceptances and terms_acceptances: who accepted which document, when, from where.
  • auth_failures: failed sign-ins (cleared after 24 hours).

There is no alerting on these logs and no scheduled access review; the access review is a manual task from the 2026-10-09 note.

What changed in release r114 (2026-11-25)

  • The Ops Console is merged into the Team Console: one sign-in.
  • Team sign-in can use a text code through the same Twilio Verify service as the portal. No separate key.
  • Team sign-in or the admin token is accepted on every staff route; audit labels now name the person ("Team: name").
  • New real-account workspace routes (connections, team access, invoices, agreements), each written to the access log; read-only role blocked from writes.
  • Legal documents tracked per client in account_legal_docs (status and dates only; signed files are not stored).
