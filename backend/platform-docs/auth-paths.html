Sign-in and account creation paths

Snapshot 2026-08-19, updated against the code 2026-11-25

The five ways a person gets into Verilume, step by step. The original flow charts and code excerpts were captured on 2026-08-19; each section here adds what has changed since, checked against the code on 2026-11-25.

Source: "Verilume: the 5 auth paths, flow chart vs. code" (PDF, snapshot 2026-08-19). The charts are rewritten as steps below, and the line numbers in that PDF have moved. Use function names to find the code.

1. Direct path: home page to log in (existing account) Fixed 08-19

Before the fix there was no Log in link on the marketing site, and a successful login kept using whatever account id happened to be in the page address instead of the account the login belonged to.

  1. Visitor clicks Log in in the site navigation (index.html links to account.html).
  2. account.html opens with no account id and asks the server for the account. The server answers 401 unauthorized, so the login box appears.
  3. Visitor submits email and password to POST /api/auth/login-user.
  4. Inactive user: 403 account deactivated. Wrong credentials: the box stays open with an error.
  5. Success: if the server says mustChangePassword, the forced password-change screen runs (POST /api/auth/change-password).
  6. The page compares the returned account id with the one in the address. If different, it saves the session for the returned account and reloads account.html?accountId=... (the 08-19 fix). If the same, the account loads signed in.

The server rule behind it: requireAccount(req,res,accountId) reads the session token and returns 401 unless the token's account equals the account being requested.

Changed since 08-19

  • A second step was added (2026-08-20): after the password, a 6-digit code is sent by email (or text if the person turned it on) through /api/auth/request-login-mfa and /api/auth/verify-login-code. A device can be trusted for 30 days.
  • Lockout (2026-11-21, r91): 10 failures for one name or 40 from one network inside 15 minutes pauses sign-in.

2. Create a new account with no assessment Worked before 08-19

Someone arrives at onboarding.html cold and creates a real account and a real admin login.

  1. Intro: company name, admin name and admin email.
  2. Optional: sign the NDA (kept for the session only).
  3. runProvisioning() calls POST /api/accounts with blank industry and description.
  4. Then POST /api/auth/register-admin creates the admin member with a temporary password and mustChangePassword set.
  5. Acceptance rows are written to legal_acceptances (document, version, name, email, IP, browser).
  6. The temporary password is shown once. "Manage your account" opens account.html.

3. Complete the assessment, then create an account to save Fixed 08-19

Three bugs were fixed here: the Save button was a stub that never called the backend, the Portal-activation button bypassed registration through the old access-code path, and onboarding links dropped the assessment data.

  1. On any assessment step the visitor clicks Save & schedule, or on the report step clicks Activate in Portal. Both open the same Save modal asking name and email.
  2. submitSaveAccountModal() calls POST /api/accounts with the full assessment payload, then POST /api/auth/register-admin.
  3. The session token is saved for that account and the temporary password is shown in the page.
  4. From Save the visitor stays on the assessment. From Activate in Portal the portal opens signed in.
  5. Alternatively the report's paid-program links open onboarding.html with the assessment data carried in the address (handoff=, base64). onboarding.html reads it, pre-fills company, name and email, and continues as path 2.
Privacy note: the assessment hand-off carries answers in the web address. Addresses end up in browser history and logs. Replacing it with a short server-held token is worth doing.

4. Select a paid account level, then create the account Gap on 08-19

On 08-19 there was no package or tier selector anywhere. "Choosing a paid level" and "creating an account" were the same path as 2 and 3, and no choice was recorded; the paid-inclusions grid on the report page was marketing copy only.

Changed since 08-19

  • Account level is now set by the Verilume team in the Team Console. The level route requires an IO reference above the free trial, and records the change in level_activations with who made it. See the staff guide.
  • Accounts carry paidTier, paidTierActivatedAt, trialpath and Terms acceptance fields.
  • I found no visitor-facing level selector in the code; a visitor still cannot choose a level themselves. Confirm if one was built elsewhere.

5. Team member invite Gap on 08-19, since built

On 08-19 POST /api/accounts/:id/team created a roster row without any password fields, so an invited person could not sign in. This was recorded as deliberate sequencing (single admin or CMO first).

Changed since 08-19

  • Invites now exist: invite email, a set-password link valid 7 days (/api/auth/invite-info shows first names only; /api/auth/reset-password completes it), and tracking on the member row (invitesentat, invitestatus, inviteerror, invitevia).
  • An admin can now deactivate a team member; so can Verilume staff from the console.

Verilume team sign-in (not in the original document)

  1. Open /platform. Email and password.
  2. Choose email or text for the 6-digit code. Text uses Twilio Verify, the same service as the client portal.
  3. Session lasts 12 hours. View-as into a client lasts 4 hours.
